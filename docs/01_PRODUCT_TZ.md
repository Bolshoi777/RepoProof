# RepoProof — полное техническое задание (Product Requirements Document)

**Редакция:** v1.0, 2026-10-08. **Тип:** проверяемая продуктовая спецификация.
**Клиент:** пользователь Windows / разработчик / maintainer.
**Фокус:** первое независимое использование публичного GitHub-проекта.

## 1. Problem statement

Обычный CI подтверждает тесты автора в подготовленном окружении. Новый пользователь действует иначе: читает README, устанавливает зависимости, создаёт окружение, запускает первую команду и ждёт реального результата. Эти два пути могут расходиться. Инструменты запуска Markdown или построения окружения уже существуют. Конкурировать одной поддержкой запуска команд бессмысленно.

**Центральная гипотеза:** программа способна независимо, повторяемо и с доказательствами установить, исполняется ли объявленный «путь первого пользователя» и выполняется ли конкретное проверяемое обещание продукта. Отчёт должен объяснять первую известную точку расхождения.

| Персона | Задача | Ценный результат |
|---|---|---|
| Новый пользователь GitHub | «Работает ли этот инструмент?» | Быстрая проверка поддерживаемого сценария без ручного развёртывания |

## 3. Value proposition

**Обещание пользователю:** `From a clean checkout to verified first useful result.`

Программа НЕ обещает найти любые дефекты, подтвердить безопасность приложения, проверить всю функциональность, обходить DRM, извлекать секреты или проверять все языки программирования.

## 4. Объём v1 и exclusions

**IN:** Windows desktop/CLI; GitHub HTTPS read-only; локальная папка; Python CLI / Node CLI / HTTP-сервис; первичный статический анализ; выделение шагов по README; план для согласования; контролируемое исполнение; встроенные доказательства; HTML+JSON-отчёты; простые фикс-кандидаты; JSON/YAML proof contract; CI mode.

**OUT v1:** private repos/OAuth, произвольные GitHub Actions, Docker Compose с несколькими сервисами, нестандартные виртуальные машины, высокопривилегированные приложения, нативные Windows GUI, Android/iOS, macOS tests, CUDA/GPU, закрытые платные APIs, безусловная поддержка package managers, полнофункциональный AI-агент исправлений, публичный SaaS-исполнитель, универсальная защита от вредоносного ПО.

## 6. State machine

`NEW -> INSPECTING -> PLANNED -> WAIT_APPROVAL -> PREPARING_WORKER -> INSTALLING -> LAUNCHING -> VERIFYING -> COLLECTING -> COMPLETE`.

Возможны `CANCELLED`, `BLOCKED_SECURITY`, `ERROR_INTERNAL`, `INCONCLUSIVE`. Нельзя переходить в `INSTALLING`, минуя подготовленный worker и approval. Внешний disconnect не означает успех: `INCONCLUSIVE` либо конкретный инфраструктурный error.

## 7. Статусы в отчёте — строгая семантика

| Статус | Когда присваивать |
|---|---|
| `VERIFIED` | Функциональный oracle пройден, evidence сохранилось, sandbox допустим, report valid |
| `BEHAVIOR_FAIL` | Install+launch выполнены, oracle проверен и не пройден |
| `LAUNCH_FAIL` | Не удалось запустить в проверенных условиях |
| `INSTALL_FAIL` | Установка завершилась ошибкой, воспроизводимой на поддерживаемом окружении |
| `DOCS_FAIL` | Документированная команда/путь фактически несогласованы с репозиторием; приведён источник |
| `PARTIAL` | Есть доказательства установки/запуска, но нет полного поведенческого oracle |
| `INCONCLUSIVE` | Не хватает предпосылок, секретов, стабильного окружения, нет надёжного verdict |
| `UNSUPPORTED` | Стек/система/сценарий вне области поддерживаемого исполнителя |
| `BLOCKED_SECURITY` | Нет аттестованного worker, нарушена execution policy или доступ небезопасен |
| `ERROR_INTERNAL` | Ошибка самого RepoProof, не баг анализируемого проекта |
| `CANCELLED` | Пользователь остановил исполнение |

Тестовый набор обязан намеренно проверять отсутствие false-positive `VERIFIED`.

## 8. Полные сценарии взаимодействия

### UC-01 Новый пользователь
1. Вставляет URL.
2. Получает inspect summary без кода исполнения.
3. Видит найденные команды и ограничения.
4. Подтверждает испытание, если worker доступен.
5. В отчёте получает трёхуровневый результат Setup → Launch → Behavior.
6. Экспортирует HTML/JSON или копирует понятную ошибку.

### UC-02 Maintainer
1. Добавляет `repoproof.yaml` с контрактом.
2. Выполняет `repoproof verify . --contract repoproof.yaml --json out.json` в специально разрешённом CI executor.
3. Получает предсказуемый non-zero код на проверенном сбое.
4. При issue прикладывает evidence report.

### UC-03 Неизвестный репозиторий
1. Нельзя уверенно вывести команды, несколько конфликтных Quick Start.
2. RepoProof предлагает выбор, указывает неопределённость.
3. Не исполняет опасный или неопределённый план без одобрения.
4. Если oracle отсутствует, итог не выше `PARTIAL`.

## 9. Не-функциональные требования

- **Offline-first:** отчёты, история, GUI работают без внешнего сервера; clone/npm/pip могут требовать сеть на разрешённой фазе.
- **Windows:** целевой Windows 11 x64, Windows 10 проверять отдельно перед заявлением поддержки.
- **Predictability:** детерминированные fixture-тесты; единые коды выхода CLI; каждое поле JSON schema-validated.
- **Accessibility:** клавиатура, масштаб 125/150%, цвет + текст статуса, contrast.
- **Performance targets (тестируемые цели, не обещания):** inspect небольшого локального проекта <3s при типичной конфигурации; HTML 10 MB без зависания; UI отзывчив при execution.
- **Storage:** явная очистка workspaces; ограниченные логи; опциональное шифрование истории позднее.
- **Privacy:** без телеметрии в v1 по умолчанию; без обязательного аккаунта.
- **Trust:** репозиторий и README — недоверенные данные и не инструкции для AI-агента.

## 10. Минимальные гарантии качества

- 30+ негативных/позитивных контролируемых scenarios; минимум 10 отдельных security scenarios.
- Без false VERIFIED на fixture-suite; независимый публичный репозиторий из поддерживаемого класса проходит end-to-end.
- Каждый заявленный статус можно воспроизвести на фикстуре.
- HTML-отчёт не исполняет HTML/JS, попавший в stdout/README.
- Windows `.exe` установлен и проверен на чистой тестовой машине с зависимостями installer/runtime.
- Открытая лицензия OSI до публикации, публичные сборки с контрольными суммами; сканирование зависимостей и секретов.

## 11. Принцип честной коммуникации

Не писать «проект безопасен», «все функции работают», «проверены любые GitHub-проекты». Писать «verified specific behavior under specified environment». В отчёте показывать границы, в которых сделан вывод.
